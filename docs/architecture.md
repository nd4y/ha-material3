# Подключаемый Material 3 для Home Assistant

Этот документ - **исторический проект от 17.10.2026**. Для текущей реализации используйте [архитектуру контроллера](controller-architecture.md), [блок-схемы](automation-flow.md) и [справочник конфигурации UI](configuration.md). Ниже сохранены исходные варианты поставки; они не являются статусом установленной версии.

## Варианты поставки

| Вариант | Возможности | Ограничение | Сопровождение |
| --- | --- | --- | --- |
| A. YAML theme | Цвета, типографические переменные и доступные параметры штатного HA | Не заменяет геометрию и поведение карточек, редакторов и диалогов | Наименьшее |
| B. UI Kit + theme | Собственные карточки климата, камер, устройств, сценариев; общий набор токенов; обычные Lovelace views и редактор | Штатная оболочка HA остаётся; чужие карточки не становятся M3 автоматически | Умеренное |
| C. UI Kit + собственная панель + theme | Всё из B плюс единая компоновка, внутренняя навигация, адаптация и диалоги внутри панели | Собственный редактор/конфигурация панели; администрирование HA остаётся штатным | Наибольшее из этих трёх |

Рекомендация для заявленной точности: C как целевой пользовательский интерфейс, B как совместимый способ использовать те же карточки в обычных дашбордах. Начать с общего UI Kit, а не разрабатывать две отдельные реализации климата. Если главный приоритет - простая установка и штатный визуальный редактор, первым релизом выпускать B. Одного A для показанного макета недостаточно.

Макет показывает область будущего модуля. Он не доказывает замену внешней панели навигации и всех административных экранов HA. Не скрывать системную навигацию обходами закрытого DOM. В документации отдельно обозначать границу, внутри которой проверяется Material 3.

## Разделение ответственности

```text
Material tokens + typography + motion + localization
                      |
        prefixed UI primitives / components
                      |
       HA adapter: state, capability, actions
                /                  \
      Lovelace cards          optional panel / view
                      |
        user-owned configuration and entity bindings
```

Предлагаемая структура production-проекта:

```text
src/tokens/          generated design tokens and profiles
src/components/      independent M3 primitives, prefix ha-m3-
src/cards/           climate, camera, device, scene cards
src/ha/              typed HA adapter, state/capability normalization
src/editor/          entity selectors and validation
src/panel/           optional navigation and composition
src/localize/        ru/en strings and number/unit formatting
themes/              generated companion YAML theme
examples/            generic entity IDs, no private installation data
```

Контракт конфигурации должен быть версионирован. Пример в `examples/proposed-dashboard.yaml` - предложение полей будущего компонента. Такой компонент пока не зарегистрирован, вставлять пример в рабочий HA рано.

Entity ID, камеры, сценарии, подписи и комнаты задаются конфигурацией. Диапазоны и шаг регулятора берутся из атрибутов привязанной сущности. Состояния `unknown`/`unavailable`, отсутствие камеры, readonly и неподдерживаемые возможности должны давать понятный интерфейс без фиктивных значений. Выбор режима определяется реальными HA-состояниями или явно привязанной сущностью, не последней нажатой кнопкой.

Модуль показывает данные и вызывает разрешённые HA actions. Он не переносит термостатическую автоматику в браузер, не рассчитывает физическое отключение по локальному таймеру и не дублирует существующие scripts/automations. Для максимального проветривания обратный отсчёт читается из сущности HA timer. Изменение вентиляции само по себе не записывает комнатную цель.

Адаптер использует переданный HA объект `hass`, стандартные действия/навигацию и `hass-more-info`, когда это уместно. Не требуются новый логин, личный access token в YAML, облачный backend, firmware patch или отдельная база. Production шаблоны должны использовать безопасные текстовые bindings Lit, а не вставлять пользовательские строки через `innerHTML`. Произвольные JS-шаблоны и `eval` в конфигурации не нужны.

## Компоненты и совместимость

У официального `@material/web` сейчас статус maintenance mode. Это хороший референс Baseline, но не гарантия поддержки новых Expressive-компонентов. На странице M3 Button groups поддержка Expressive для Web обозначена как unavailable. Поэтому нельзя обещать, что обновление npm автоматически обеспечит соответствие последней спецификации.

В прототипе официальные `md-*` компоненты исполняются в отдельном preview iframe. В HA нельзя просто зарегистрировать второй комплект глобальных `md-*`: возможны конфликты с HA и другими ресурсами. Production UI Kit должен иметь свой префикс `ha-m3-*` и документированный runtime. Варианты реализации: небольшие собственные Lit-компоненты по спецификации с визуальными тестами или сопровождаемая сборка выбранных примитивов с полным префиксованием внутренних тегов. Простого alias верхнего класса недостаточно, если шаблоны продолжают создавать глобальные `md-*`.

Для отдельной панели существует официальный `panel_custom`, включая `embed_iframe` для конфликтующих web components. Такой изолированный вариант проще для runtime, но добавляет обязанности по теме, фокусу и обмену данными; это не способ подменить весь HA frontend. Регистрация panel_custom в configuration.yaml требует перезапуска HA, что учитывать при будущем внедрении. Для встраиваемых карточек нужна отдельная проверка отсутствия конфликтов.

Не делать форк HA frontend, CSS-селекторы к его закрытым внутренним структурам или зависимость от card-mod обязательной частью дизайна. Не брать неподдерживаемые переменные HA за стабильный API. Общий M3 token set переводить в ограниченный HA theme mapping, а собственные компоненты читают свои токены напрямую.

## HACS и GitHub

Для frontend UI Kit - HACS Dashboard plugin: JS bundle в корне или dist, имя bundle согласовано с именем репозитория. Для theme - YAML в `themes/<name>.yaml`; у HACS отдельные требования к этому типу репозиториев. Не обещать автоматическую установку JS и активацию YAML-темы одним обычным Dashboard resource.

Практические схемы:

1. Один репозиторий `ha-material3`: HACS устанавливает frontend plugin; companion theme публикуется отдельным release asset с явной инструкцией копирования и включения. Сам UI Kit может работать без глобальной theme.
2. Два связанных репозитория `ha-material3` и `ha-material3-theme`: каждый устанавливается HACS своим штатным типом. Общие токены/версия генерируются одним release pipeline, а не копируются вручную.

Предпочтение для первого публичного релиза - схема 1: одна кодовая база, необязательная theme. Для удобного распространения theme через каталог HACS позднее добавить схему 2.

Релиз содержит локальные JS/fonts/icons, лицензии, generic examples, поддержанные версии HA/браузеров, changelog и миграцию config_version. CI: build, типы, lint, проверка отсутствия приватных данных, контраст, accessibility и screenshot regression по выбранному M3 профилю. Матрицу совместимости заполнять реальными результатами, не предполагать совместимость со всеми версиями HA.

Обновления не меняют entity registry, автоматизации и предпочтения пользователей без явного действия. Откат: прежний frontend release/theme и конфигурация дашборда. Перед первым live внедрением - checkpoint ресурсов, panel/dashboard config и theme settings.
